# Contributing to Lunix

Спасибо за вклад в Lunix.

Главное правило проекта простое: **любой качественный вклад, который реально работает и не ломает существующее поведение, будет принят**.

Это правило распространяется и на чистый, наглый вайб-код. Неважно, насколько необычно или хаотично ты пришёл к решению. Важно, чтобы результат был рабочим, проверяемым, понятным для поддержки и соответствовал требованиям ниже.

## Жёсткий стандарт приёма

Pull request принимается только если одновременно выполнены все условия:

- изменение решает заявленную задачу;
- Lunix запускается после изменения;
- существующие команды и syscall-модули не ломаются;
- нет ошибок Lua, синтаксических ошибок и очевидных runtime-проблем;
- поведение проверено командами или тестовым сценарием;
- изменённый код соответствует текущей структуре проекта;
- описание pull request честно объясняет, что изменилось и как это проверялось;
- в diff нет случайных файлов, временных данных, секретов и изменений, не относящихся к задаче;
- новые ошибки обрабатываются в стиле проекта через основной результат и код ошибки, если это относится к filesystem API;
- изменение не создаёт доступ к файлам за пределами виртуального корня `luafs/`.

Если хотя бы один пункт не выполнен, pull request отправляется на исправление или закрывается до доработки.

## Vibe-код разрешён

Lunix не требует академически идеального кода и не запрещает странные, быстрые или экспериментальные решения.

Vibe-код принимается, если он:

- работает на заявленной платформе;
- не маскирует ошибки;
- не ломает публичное поведение;
- не содержит мёртвых кусков, случайного debug-вывода или временных костылей;
- может быть проверен другим человеком;
- не усложняет поддержку настолько, что следующую ошибку невозможно локализовать;
- не нарушает правила безопасности виртуальной файловой системы.

Красивый код, который не работает, не принимается. Некрасивый код, который стабильно работает, понятен и проходит проверки, может быть принят.

## Что можно отправлять

Приветствуются:

- новые команды в `programs/`;
- новые syscall-подобные операции в `modules/syscalls/`;
- исправления ошибок в shell и виртуальной файловой системе;
- улучшения обработки ошибок;
- улучшения совместимости с Linux, Unix и macOS;
- документация и рабочие примеры;
- небольшие экспериментальные функции, если они не ломают текущий API.

## Перед началом работы

1. Проверь, что задача ещё не решена в открытом pull request или issue.
2. Выбери одну понятную задачу на один pull request.
3. Не смешивай исправление ошибки с несвязанным рефакторингом.
4. Убедись, что изменение не требует неподтверждённых зависимостей.
5. Если меняешь публичное поведение, опиши это в pull request.

## Требования к командам

Новая команда должна быть отдельным Lua-файлом в `programs/` и возвращать таблицу такого вида:

```lua
local command = {
    name = "example",
    desc = "Краткое описание команды",
    run = function(shell, args)
        -- Проверка аргументов и рабочая логика команды.
    end
}

return command
```

Для команды обязательно:

- уникальное и понятное поле `name`;
- короткое поле `desc`, которое нормально отображается через `help`;
- корректная проверка количества и содержания аргументов;
- понятное сообщение об ошибке для пользователя;
- обработка ошибок filesystem API без падения всей оболочки;
- отсутствие записи за пределы `luafs/`;
- проверка командой `help` и отдельным сценарием использования.

## Требования к syscall-модулям

Новый syscall должен:

- загружаться через существующую систему в `modules/fs.lua`;
- получать общий `context`, а не создавать отдельное состояние без необходимости;
- возвращать согласованный результат и `context.errno.*` при ошибке;
- проверять типы и недопустимые аргументы;
- корректно закрывать открытые файловые и каталоговые дескрипторы;
- не обходить `context.resolve`;
- работать как с абсолютными, так и с относительными виртуальными путями, если это относится к операции;
- быть добавлен в список `syscallNames`, если он должен стать публичным методом `filesystem`;
- иметь проверку успешного и ошибочного сценария.

Файл syscall-модуля должен следовать существующему шаблону фабрики:

```lua
return function(context)
    return function(path)
        -- Проверка аргументов и операция.
    end
end
```

## Проверка перед отправкой

Из корня репозитория выполни:

```bash
meson setup build
meson compile -C build run
```

В запущенной оболочке минимум проверь:

```text
help
version
ls
touch contribution-test.txt
cat contribution-test.txt
rm contribution-test.txt
exit
```

Если изменение связано с каталогами или syscall API, добавь ручные проверки именно для изменённого поведения: успешный сценарий, неверные аргументы, отсутствующий объект и повторное использование закрытого дескриптора, если применимо.

Перед отправкой также проверь diff:

```bash
git diff --check
git status --short
```

В `git status` и diff не должны попадать временные файлы, содержимое `build/`, скомпилированные `*.luac`, локальные настройки редактора или случайно изменённые файлы.

## Pull request

Название pull request должно коротко описывать результат, например:

```text
Add mkdir shell command
Fix virtual path traversal handling
Add lseek syscall support
```

В описании укажи:

- что изменилось;
- зачем это нужно;
- как проверить результат;
- какие команды были выполнены;
- есть ли ограничения или несовместимости.

Не объявляй изменение полностью готовым, если проверял только синтаксис. Рабочий сценарий должен быть проверен запуском Lunix.

## Обязательное поведение ревью

Ревью проверяет прежде всего результат, а не личный стиль автора.

Ревьюер вправе потребовать исправления, если изменение:

- не запускается;
- ломает существующую возможность;
- не обрабатывает ожидаемую ошибку;
- нарушает границы `luafs/`;
- добавляет ненужную зависимость;
- содержит непроверенное поведение;
- ухудшает совместимость с заявленными Unix-подобными системами;
- не позволяет понять, как проверить результат.

Ревьюер не должен отклонять рабочий вклад только потому, что автор использовал другой стиль реализации. Стиль важен после корректности, безопасности и проверяемости.
